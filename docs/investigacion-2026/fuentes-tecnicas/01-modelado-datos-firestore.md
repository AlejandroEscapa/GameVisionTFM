# Dimension 01: Modelado de datos Firestore para escalar

> Investigación de arquitectura de datos para GameVision (Android nativo, Kotlin + Compose, Firestore como BD principal), modelo F0-B: `users/{email}/library/{gameId}`, `users/{email}/logs/{logId}`, `users/{email}/sessions/{sessionId}`.
> Fuente prioritaria: documentación oficial `firebase.google.com/docs/firestore` y `docs.cloud.google.com/firestore` (consultada 2026-09-28). Fecha de última actualización de las páginas oficiales: **2026-09-24 UTC**.
> Advertencia de método: el buscador web disponible devolvió resultados ruidosos; por eso la evidencia dura se extrajo **directamente de las páginas oficiales** (fetch HTTP), no de snippets.

### Current State

- **Tres opciones canónicas de estructura**: Firestore ofrece `documents`, `multiple collections` y `subcollections within documents`; la elección depende del caso de uso [^fs-hier].
- **Anidar (map/array dentro del documento)** es válido para listas "simples y fijas"; el límite oficial dice que *"This isn't as scalable as other options, especially if your data expands over time. With larger or growing lists, the document also grows, which can lead to slower document retrieval times."* [^fs-hier]. Es decir: anidar sirve para instantáneas pequeñas, no para datos que crecen.
- **Subcolecciones**: *"As your lists grow, the size of the parent document doesn't change. You also get full query capabilities on subcollections, and you can issue collection group queries across subcollections."* Limitación explícita: *"You can't easily delete subcollections."* [^fs-hier].
- **Colecciones raíz**: buenas para relaciones muchos-a-muchos y consultas potentes, pero *"Getting data that is naturally hierarchical might become increasingly complex as your database grows."* [^fs-hier].
- **Regla estructural dura**: *"A collection contains documents and nothing else. It can't directly contain raw fields with values, and it can't contain other collections."* [^fs-modeling].
- **Filosofía de diseño**: *"Cloud Firestore is optimized for storing large collections of small documents."* [^fs-modeling].
- **Denormalización / "no hay joins"**: Firestore es una BD de documentos sin `JOIN`; los joins se simulan **duplicando datos** en varios sitios, y la contrapartida es el riesgo de inconsistencia [^fs-denorm-media][^fs-njoins-media]. La doc oficial de Firestore no prescribe un patrón de fan-out con nombre propio en las páginas consultadas; se apoya en el principio de modelar según consultas.
- **Hotspots — causas oficiales**: crear documentos a muy alta tasa con IDs propios monotónicamente crecientes; crear documentos a alta tasa con un *campo* monotónicamente creciente (p. ej. timestamp); crear documentos en una colección con pocos documentos; borrar a alta tasa; y subir tráfico sin rampa [^fs-bp].
- **IDs automáticos mitigan hotspots**: *"Cloud Firestore allocates document IDs using a scatter algorithm. You should not encounter hotspotting on writes if you create new documents using automatic document IDs."* [^fs-bp].
- **Campo secuencial indexado ⇒ límite de 500 escrituras/segundo**: *"If you index a field that increases or decreases sequentially between documents in a collection, like a timestamp, then the maximum write rate to the collection is 500 writes per second."* [^fs-bp]. Este **no** es un límite de documento, es un límite de **colección** cuando se indexa un valor secuencial.
- **Regla 500/50/5**: arrancar como máximo a 500 operaciones/segundo en una colección nueva y luego subir hasta un 50% cada 5 minutos, distribuyendo las operaciones por el rango de claves [^fs-bp][^fs-scale].
- **Contención en un solo documento**: *"Avoid high read or write rates to a single document, or documents in a key range containing a few documents, or your application will experience high latency and/or contention errors."* [^fs-scale]. La doc **evita dar una cifra fija**: *"The exact maximum rate that an app can update a single document depends highly on the workload."* [^fs-bp].
- **Contadores distribuidos**: no se puede actualizar un documento a tasa ilimitada; con incrementos frecuentes aparece contención. Solución oficial = **documento contador con subcolección de `shards`**; *"Each shard can support being incremented once per second"*, y *"a distributed counter with 10 shards can handle 10x as many writes as a traditional counter."* [^fs-counters]. Es el fundamento oficial del ~1 escritura/segundo por documento/entidad.
- **`FieldValue.increment()`**: el patrón de incremento atómico es el que usa la propia solución de contadores (`shard_ref.update("count", FieldValue.increment(1))`), que evita leer-y-escribir y reduce contención [^fs-counters].
- **Índices de un solo campo son automáticos**: *"By default, Cloud Firestore automatically builds indexes for each field present in the documents in a collection."* Pero *"Cloud Firestore doesn't automatically create indexes for combinations of fields"* — si la query no tiene índice, devuelve error con link para crearlo [^fs-index].
- **Índices compuestos (igualdad + rango)**: para combinar `==` con operadores de desigualdad (`<`, `<=`, `>`, `!=`) se necesita un **índice compuesto** [^fs-query]. La doc oficial explica que el orderBy implícito suele obligar a índice compuesto.
- **Límites de consulta**: máximo **30 disyunciones** en forma normal disyuntiva (*"This limit is fixed and cannot be adjusted."*); `in`/`array-contains-any` combinan hasta 30 cláusulas de igualdad; máximo **una** cláusula `array-contains` por disyunción y no se puede mezclar con `array-contains-any` [^fs-query].
- **Collection group**: un "collection group" = todas las colecciones con el mismo ID; para filtrar/ordenar en una collection group query **hay que crear el índice con scope de collection group** [^fs-query][^fs-index].
- **Paginación**: prohibido `offset`; usar **cursores**. *"Do not use offsets. Instead, use cursors. Using an offset only avoids returning the skipped documents to your application, but these documents are still retrieved internally... your application is billed for the read operations required to retrieve them."* [^fs-bp]. `startAt()` incluye el punto, `startAfter()` lo excluye; `endAt()`/`endBefore()` cierran el rango [^fs-cursors].
- **Tamaño máximo de documento**: **1 MiB (1,048,576 bytes)**; tamaño máximo de un valor de campo **1 MiB − 89 bytes**; profundidad máxima de map/array **20 niveles**; profundidad de subcolecciones **100**; máximo **40.000 entradas de índice por documento**; valor de campo indexado máx. **1500 bytes** (los mayores se truncan y pueden dar resultados inconsistentes) [^fs-limits].
- **Límites de escritura/transacción**: tamaño máx. de petición API **10 MiB**; tiempo máx. de transacción **270 s** con expiración por inactividad de **60 s**; máx. **500 transformaciones de campo** por documento en un Commit/transacción; memoria máx. de una query **128 MiB** (edición Standard) [^fs-limits][^fs-limits-cloud].
- **Índices compuestos por base de datos**: 200 sin facturación / 1000 con facturación; máximo **100 campos** por índice compuesto; tamaño máx. de entrada de índice **7,5 KiB** [^fs-limits][^fs-index].
- **Listeners en tiempo real = snapshot listeners**: notificaciones de baja latencia; *"you are billed for the documents returned to your app and not for maintaining an open connection"* [^fs-rt]. Recomendación clave: *"Snapshot listeners that try to filter too much incoming data might be slow even if the result set is small"* y *"It might work best to break your data into smaller collections with smaller write rates."* [^fs-rt].
- **Listeners y escrituras están acoplados**: *"a write operation causing hotspots or lock contention can negatively affect read operations"*; y documentos/escrituras pequeños se procesan más rápido [^fs-rt]. *"Favor long-lived listeners"*: mantener el listener vivo lee solo lo que cambia, mientras que las one-shot re-leen datos que no cambiaron [^fs-rt].
- **Colecciones que crecen sin límite**: patrón oficial = **TTL policies** (campo timestamp que marca expiración; borrado típico en <24 h, no instantáneo, no borra subcolecciones, requiere desindexar el campo TTL para evitar hotspots) [^fs-ttl]. Para datos que deben conservarse, la vía es **paginación por cursor sobre un campo de fecha** [^fs-cursors] y/o **subcolecciones por periodo** para que el documento padre no crezca [^fs-hier].
- **Agregación server-side**: Firestore soporta `count()`, `sum()`, `average()` y solo transmite el resultado, evitando traer todos los documentos para contarlos/sumarlos [^fs-agg].

### Tensions & Counter-arguments

- **"1 escritura/segundo por documento" NO es un límite oficial con cifra.** La documentación oficial de *best practices* evita la cifra y dice que la tasa máxima "depende altamente de la carga de trabajo" [^fs-bp]. El dato de "~1/s" solo aparece de forma indirecta en la solución oficial de contadores ("cada shard puede incrementarse una vez por segundo" [^fs-counters]) y de forma explícita en medios técnicos [^fs-rate-media]. **Implicación para GameVision**: no asumir un techo duro de 1/s por documento; sí evitar *diseñar* un documento que reciba escrituras concurrentes de alta frecuencia (p. ej. un contador global de minutos).
- **El límite de 500 escrituras/segundo es de *colección con campo secuencial indexado*, no de colección "normal".** Si en `sessions/{sessionId}` se indexa `fecha` (timestamp) y se escriben muchas sesiones a la vez en la misma colección, se acerca al techo de 500/s de esa colección; la mitigación oficial es **eximir de índice** el campo secuencial si no se consulta por él [^fs-bp]. Con decenas de miles de usuarios el riesgo es real solo en picos de escritura masiva, no en uso orgánico.
- **Subcolecciones vs colecciones raíz — tensión de agregación.** Bajo `users/{email}/...` cada documento es pequeño y aislado por usuario (bueno: sin contención entre usuarios; malo: no se pueden hacer consultas globales tipo "top juegos" sin *collection group queries*, que **exigen índices con scope de collection group** y no se crean solos) [^fs-index][^fs-hier]. Un modelo mixto (subcolecciones por usuario + colecciones raíz de agregados) suele ser necesario si el producto quiere funciones sociales/estadísticas — pero es justo lo que el modelo F0-B no contempla.
- **Denormalización (instantánea de nombre/portada en `library/{gameId}`): acelera lecturas pero crea deuda de consistencia.** Es la decisión correcta para evitar un join por juego, pero si el catálogo de juegos cambia, la copia queda obsoleta; hay que aceptar consistencia eventual y decidir si se reescribe (fan-out costoso sobre N usuarios, con riesgo de superar el tamaño máx. de documento si se agrupa) o no [^fs-denorm-media]. Firestore no ofrece transacciones multi-colección gratis en coste: cada escritura del batch cuenta facturación [^fs-tx].
- **`logs` y `sessions` son colecciones que crecen sin límite (partidas y diario "durante años").** No hay límite de nº de documentos por colección, pero sí degradación de latencia y coste de lecturas al paginar colecciones enormes. Estrategias oficiales/compatibles: **paginación por cursor sobre `fecha`** (nunca `offset`) [^fs-bp][^fs-cursors], **subcolecciones por periodo** para que el padre no crezca [^fs-hier], **TTL** para datos prescindibles (ojo: TTL no borra subcolecciones y su borrado no es instantáneo) [^fs-ttl], y **archivado** fuera de Firestore. La doc oficial **no** ofrece un patrón único "time-series" con nombre; es una inferencia a partir de las guías de modelado, TTL y cursores.
- **Contra-argumento a los contadores distribuidos**: introducir shards añade complejidad (hay que leer N shards y sumar, o mantener un total agregado) [^fs-counters]. Alternativa moderna: **consultas de agregación `sum()`/`count()` server-side**, que evitan mantener contadores a mano y solo transmiten el resultado [^fs-agg] — más simple, aunque re-escanear índices no es gratis.
- **Listeners en tiempo real a escala**: la doc advierte que un listener sobre una colección muy grande y con mucho *churn* obliga a conectar con muchos servidores y puede ser lento aunque el resultado filtrado sea pequeño [^fs-rt]. Contradice la intuición de "listener sobre todo `users/{me}` y listo": conviene **listeners por documento o por colecciones pequeñas y de bajo cambio**, y para alto volumen de datos usar **one-shot queries de baja frecuencia** en lugar de listeners [^fs-rt].
- **El límite clásico "500 documentos por batch/transacción" ya no figura en la página oficial de límites (2026-09-24)**: esa página solo lista "500 transformaciones de campo por documento en un Commit/transacción" [^fs-limits]. Los medios siguen citando el límite de 500 documentos por lote [^fs-batch-media]. **Confianza media**: al diseñar importaciones/backfill, no asumir un límite distinto del documentado y preferir *bulk writer* (que la propia doc recomienda frente al batch atómico para grandes volúmenes) [^fs-bp].
- **Recomendación oficial específica para "bibliotecas/historiales/diario por usuario": no existe una página con ese nombre.** La guía aplicable es genérica: datos que crecen ⇒ subcolecciones [^fs-hier]; listas fijas y pequeñas ⇒ anidar en el documento del usuario [^fs-hier]. La profundidad >2–3 niveles como "mala práctica" es folclore de comunidad (confianza baja) [^fs-nest-media], no regla oficial.
